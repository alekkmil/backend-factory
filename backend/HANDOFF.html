2. CMS and content architecture

Proposed default: a separate headless CMS with structured collections, PostgreSQL and object storage, exporting versioned approved content snapshots. The Next build/server consumes approved snapshots with a server-side credential; browsers never receive CMS admin tokens or drafts. The previous WordPress archive remains a read-only source and is not the new backend.

Directus is a concrete candidate, not an approved purchase/version: its official documentation covers translation collections and content versions. Confirm the pinned release, licensing eligibility, asset storage support and required role/workflow controls before selection. Another CMS is acceptable if it passes the same portable model and editor acceptance checks. Git-only JSON editing is not the proposed nontechnical editor workflow.

content-model.json defines 12 entities: Page, PageLocale, Section, Route, ContactProfile, MediaAsset, Navigation, Action, Enquiry, NotificationOutbox, RedirectDecision and Release. Stable page/section IDs link languages independently of URL spelling. Store original IDs, sources, revision and approval references. Keep explicit ordered section IDs; do not let translation or CMS sorting reorder the old site.

  1. An editor drafts BG copy/facts/assets and records the source or accepted decision.
  2. A BG revision marks affected EN records stale. The translator updates all corresponding blocks, FAQ, action labels, messages, metadata, alt and meaningful image text.
  3. A reviewer checks facts, full BG/EN parity, known missing assets and destinations in protected preview. Ordinary EN translation requires no new client authorization.
  4. A publisher promotes a paired, versioned content snapshot. A signed webhook or explicit release triggers CI; it cannot supply arbitrary code/URLs.
  5. Build gates reject stale EN, missing required sections/assets, invalid URLs and unauthorized facts. Failed publication leaves the previous accepted public snapshot intact.

Roles are editor, translator, reviewer, publisher and administrator, with only required permissions. Small teams may assign multiple roles to a person, while publish/schema authority remains explicit. Public CMS access exposes only the published projection. Enquiry records are private operational data, excluded from public CMS queries and ordinary content editing.

Prepare domain/locale/path configuration for a separate future .it domain. Confirm its exact name/ownership and Italian content before enabling it. Do not create an empty /it version, publish missing translations or silently redirect visitors by IP/browser language.

4. Durable acceptance, delivery, retries and errors

  1. Check method/content type/body size, same-origin policy, rate limit and spam checks; validate the payload/context. POST to the public JSON endpoint is the only submission action; other methods return 405. A challenge can be introduced by configured policy, with an accessible alternative and explicit challenge_required response.
  2. Within one database transaction, claim the idempotency key, persist the validated encrypted enquiry and create one NotificationOutbox row. Return 202 {requestId, status: "accepted"} only after durable commit. A database/queue failure is not a success.
  3. The worker reads the outbox and sends a notification to cargo@skvltd.com from a verified sender identity; the customer's validated address may be Reply-To, never From or an arbitrary destination. Include the stable request ID, kind, locale, route context and escaped field values in a fixed template.
  4. Record provider acceptance separately from delivered, delayed, bounced or failed status. SES events distinguish SEND from delivery to the recipient mail server; none proves human reading or a confirmed reservation. SES event semantics.
  5. Transient failures use bounded backoff and a dead-letter/manual recovery state. Proposed retry intervals: 1, 5 and 30 minutes, then alert. An ambiguous provider timeout may already have sent the email; retain request ID and evidence, reconcile known provider IDs and avoid blind repeated sends. This is not an exactly-once email guarantee.

Idempotency: a repeated key and normalized payload returns the same 202/requestId without another enquiry/outbox row. The same key with a changed payload returns 409. Store the key hash, payload hash and response for a proposed 24-hour window. After a network timeout the frontend retains entered fields and retries with the same key. A deliberately edited/new submission uses a new key. Do not put the payload in URLs or persistent browser localStorage by default.

Errors are machine codes plus optional fieldErrors keyed by canonical field ID: 400 malformed request; 403 origin/spam/challenge; 409 idempotency conflict; 413 size; 415 media type; 422 field validation; 429 with Retry-After; 503 cannot accept. Unsupported methods return 405 with Allow: POST (HEAD has no body); all API responses use Cache-Control: no-store. The frontend localizes codes, focuses an accessible summary/first invalid field, preserves values and provides a contact exit. It never reports success on a timeout, validation error, spam rejection or failed persistence. The accepted message says the enquiry was received for processing, with no fixed response-time promise.

Proposed shared rate limits begin conservatively at 5 submissions/minute per short-lived pseudonymous network key and 20/hour per normalized-email hash, tuned against shared-office traffic. Do not rely only on per-process memory or IP bans. Combine origin verification, server validation, payload limits and server-observed abuse signals; do not create fake success for rejected spam. No challenge vendor is selected or loaded until privacy/accessibility requirements are checked. The contract includes only optional antiSpamToken for a configured challenge policy; any extra honeypot or timing fields require a coordinated schema/UI revision.

5. Email verification, PII and secrets

SES is the proposed transactional provider. Before enabling real sending, verify the actual sender identity and region/account access; sandbox restrictions may require verifying the recipient or obtaining production access. These are prerequisites, not actions performed here. SES verified identities; sandbox / production access.

The recipient cargo@skvltd.com is approved. The sending identity, provider account, DNS authentication and real delivery are not verified. Do not change MX, SPF, DKIM, DMARC or mail routing as an incidental website task. Any required identity/DNS change is presented separately for authorization. Staging defaults to a test transport/sink with visible environment tagging; a real end-to-end delivery test is explicitly authorized and visibly marked as a test.

  • Use TLS in transit, encrypted database/object storage and IAM-restricted access. Keep enquiry data out of public content exports, Figma, Git, analytics, exception dumps and ordinary application logs.
  • Log request ID, status, kind, duration and non-sensitive error code. Do not log names, email addresses, plates, free text, raw request bodies, tokens or complete URLs with submitted data.
  • Store provider/CMS/database secrets in an environment-specific secret store; never NEXT_PUBLIC variables, source files or image layers. Runtime credentials use workload roles; rotation and least-privilege access are documented.
  • Proposed operational defaults: enquiry payload retention 30 days after processing, event/log retention 30 days, idempotency 24 hours. These are reviewable project defaults, not legal requirements. Confirm the data owner's retention/notice policy before production, including mailbox copies and backup expiry. Deletion requests must cover operational stores without corrupting audit integrity.
  • Delivery acceptance requires a test received in the actual cargo mailbox with correct reply behavior, provider delivery/bounce evidence, duplicate/retry checks and a recovery drill. A configured address, API 202, SMTP acceptance or successful build alone does not pass this test.

7. Proposed deployment topology and release behavior

Region: eu-central-1 (Frankfurt) for regional app/CMS/database/storage/email resources, subject to service/account checks. Fargate availability there is documented. CloudFront is global; its viewer ACM certificate must be in us-east-1. Do not describe that certificate/CDN control plane as EU-only data residency. CloudFront certificate region.

  • Separate staging and production accounts where available, otherwise isolated stacks, secrets, databases, buckets and identities. AWS ownership remains with SKV. No resource is provisioned by this handoff.
  • CloudFront/HTTPS in front of an access-restricted ALB and private Fargate tasks. Proposed production minimum is two web tasks across two availability zones; final sizing is a load-test decision. The CMS/admin is separate and protected by authenticated access. Public pages use the last accepted content snapshot rather than requiring a live CMS request for every visitor.
  • Use a pinned Linux image with Node 24 LTS as the test candidate; current official release data marks 24 LTS. Check Next/CMS dependency engines and native modules, then pin a patch/image digest. Do not select Node 20 solely because it meets the old minimum; it is listed EOL. Node release status.
  • Next standalone build must include public and .next/static assets, bind to 0.0.0.0 on the container port, run non-root and stop gracefully. The reference's 127.0.0.1 start binding is for local use and is not copied blindly into a container.
  • Default content publication uses a versioned rebuild/release for this small site. Keep CMS drafts and POST APIs uncacheable. Long-lived immutable assets use content hashes; HTML caching is tied to accepted release/version. If ISR is introduced, test shared-cache invalidation across every task; a local invalidation is not assumed to update all instances. ISR platform constraints.
  • Store sanitized public assets in a private S3 bucket through CloudFront OAC, with a bucket policy scoped to the distribution; do not use an S3 website endpoint for OAC. AWS OAC requirements. Keep original private archives entirely separate.
  • Private PostgreSQL stores CMS/operational data with distinct least-privilege roles/schemas. The enquiry and outbox transaction must remain atomic. A worker polls durable outbox rows with row locking; no email work relies on a request continuing after the HTTP response.

Compatibility gate: build with the pinned lockfile on the chosen Linux/Node image; boot standalone; fetch every active page/assets; test APIs, redirects, locale headers, staging protection and graceful restart; simulate CMS outage and worker retry; verify more than one web task serves the same release. Record exact versions and observed results. Nothing in the earlier local build passes this AWS gate automatically.

8. CI/CD, IAM, observability and recovery

CI runs schema/content parity checks, type/build checks, asset/URL validators and focused API tests; it creates an immutable app image and versioned content/media/routing manifests. Promote the same tested artifact to production with environment-specific configuration. Use protected production approval, health checks and rollback to the previous image/release. Database migrations are backward-compatible first; a code rollback must not erase newly accepted enquiries.

Use OIDC/federated short-lived deployment credentials, limited to the intended repository/environment/branch, instead of long-lived keys. Separate deploy, task execution, web, CMS, worker and backup roles. Scope sender permissions to the verified identity and known destination where the service supports conditions. AWS GitHub OIDC restrictions.

Alert on elevated 5xx, failed health checks, enquiry acceptance failure, oldest pending outbox age, dead-letter/unknown/bounce state, exhausted storage, failed backup and certificate expiry. Proposed initial alert: an outbox item pending over 10 minutes or any permanent delivery failure requires operator attention; tune after baseline testing. Logs include correlation IDs and non-sensitive codes only. Analytics records enquiry_accepted only after API acceptance, never email delivery or sensitive field values; nonessential analytics follows the approved consent policy.

Proposed recovery targets, to be accepted and rehearsed rather than guaranteed: database recovery point within 15 minutes and service restoration within 4 hours. Enable RDS automated backups/PITR, proposed 14-day retention, plus an explicit pre-migration snapshot; version media objects/content exports and retain previous release manifests. RDS restore creates a new instance, so the runbook includes validation and switching the application to it. RDS backup/restore behavior. Rehearse restoration in an isolated environment and verify contacts, language pairs, assets and pending enquiries.

9. Open operational choices and acceptance boundary

Page-date persistence: the user-authorized date lifecycle contract extends PageLocale with publication provenance and actual production activation dates. Import the supplied per-locale historical dates, retain unknown imported publication values as null, and assign dates for new pages only at successful public activation. Keep these values with the content revision and verify unchanged deploy, failed activation, preview and rollback behavior. Rendering/build clocks must not manufacture datePublished/dateModified/lastmod.
